# 代码与文件流程

本文描述当前实现。输出分层、失败诊断持久化及转换核心目录整理均已完成。

## 1. 先看完整流程

```text
Virtuoso 中的 library / cell / schematic
  │
  │ SKILL: VCExportCell → VCExportSchematic
  ▼
原始 snapshot.json
  │
  ├─ prepare（可选）→ mappings.json → 用户修改 → save-mappings（可选）
  │                                                │
  │                                                ▼
  │                                         personal/mappings.json
  │
  └─ convert：内置映射 + 指定的个人映射
       │
       ├─ 校验快照、扫描 master、解析映射
       ├─ 投影：省略实例/引脚、处理孤立端口
       ├─ 为未映射模块创建通用方框定义
       ├─ 筛选参数 → 精简 snapshot
       ├─ Python：生成器件、网络、基础连线和标注
       ├─ JavaScript：修正连线、衬底支线、名称位置
       ├─ 原生格式/端点/ERC/视觉校验，输出 SVG
       ├─ TypeScript：核对源与目标网络成员、接口
       └─ CLI：默认发布整个新目录；Virtuoso 窗口用 --flat 写入指定保存目录
```

正常使用不需要 Bridge。用户在 CIW 执行 SKILL 后，后续都是本机文件转换。
我们测试时使用 Bridge，是为了让测试客户端远程调用同一个 SKILL 导出函数；Bridge 不参与离线转换。

## 2. 文件树与职责

```text
virtuoso-canvas/
├─ skill/
│  ├─ export_schematic.il         Virtuoso 数据库读取与 JSON 写出
│  └─ virtuoso_canvas_ui.il       原生窗口、扫描/映射/导出编排
├─ packages/
│  ├─ cli/src/main.ts             命令解析、读写用户文件、最终输出目录发布
│  ├─ cli/src/skill-ui.ts         SKILL 固定协议与正式 CLI 的窄适配层
│  └─ virtuoso-import/           唯一转换核心；独立版和上游暂存包共用
│     ├─ index.ts                对外入口
│     ├─ core/                  快照校验、映射、个人配置及数据投影
│     ├─ adapter/               convertDesign 编排、通用方框及连接核对
│     └─ engine/                Python/JavaScript 布局与校验引擎
│        ├─ convert_canvas.py    基础转换引擎
│        ├─ snapshot_checks.py   Python 侧输入校验
│        ├─ refine_canvas.mjs    连线和标注修正的执行顺序
│        ├─ box_routes.mjs       模块出线、短末端、局部共享电源节点
│        ├─ bulk_routes.mjs      衬底支线首次接触同网主线时接入
│        ├─ native_labels.mjs    调用原生实例名称布局
│        ├─ port_labels.mjs      外部 pin 名称按朝向排布
│        ├─ label_layout.mjs     剩余标注的有限范围避让
│        ├─ segment_geometry.mjs 实际线段与矩形求交
│        ├─ validate_canvas.mjs  原生校验、ERC、视觉诊断、SVG
│        └─ presentation_config.json 默认显示配置
├─ rules/builtin/
│  ├─ mappings.json              当前日常使用的内置映射
│  └─ common.json                旧 recommend 流程的推荐规则
├─ personal/
│  ├─ config.json                 用户转换策略和显示偏好
│  └─ mappings.json               用户可复用器件映射
├─ analog-canvas/                 上游编辑器、模型、符号、校验、渲染库
├─ dist/                          TypeScript 编译产物；不要手工改
├─ schemas/                       用于说明/外部工具的生成 JSON Schema
├─ scripts/                       构建、目录生成、回归及设计测试脚本
├─ tests/                         自动化测试和合成数据
├─ docs/                          说明文档
└─ work/                          示例、实测输入输出；不是程序必须依赖的库
```

两个容易误解的地方：

- `engine/` 中的 Python 和 JavaScript 仍是正式转换链路的一部分，不是旧版兼容代码。
- `core/index.ts` 混合了公共能力与旧流程，不能因为不再使用 candidateId，就把整个文件删除。

`scripts/build.mjs` 先编译有本地扩展的上游 model/symbols/render-svg，再编译我们自己的 TS。
`dist/analog-canvas` 是指向上游目录的链接。当前运行也需要上游已安装的依赖及相关编译产物，不是拷贝一个 CLI 文件就能独立运行。

## 3. 按执行顺序理解代码

### 3.1 SKILL 提取

`VCExportCell(library cell view path)` 只读打开目标 cellView，调用 `VCExportSchematic`，最后释放自己打开的引用。

快照包含：实例、网络成员、顶层端口、原图线与标签、每个实例的 symbol 图形/引脚、实例属性、有效 CDF 参数和部分仿真元数据。
symbol 记录按实例保存，不是按不同 master 去重的器件库。

这里不做器件映射、不读取 Analog Canvas 配置、不自动 Check and Save。原图中存储的连接不准确时，导出不能自动替用户修复。
正常情况下只生成用户指定的一个快照文件。已有同名文件会拒绝，父目录需要预先存在。

### 3.2 当前映射流程

`prepareMappings` 按 library/cell 识别器件类型，以个人规则覆盖内置规则；参数值不同不会分成不同类别。
用户面对的是可读的 `devices` 映射表，不需要填写 reviewer 或 candidateId。

- `prepare`：生成当前设计的映射设置和可读预览，不写回个人规则。
- `save-mappings`：把用户设置合并到指定的个人映射文件；存在冲突时按当前命令的替换规则处理。
- `convert`：可以直接准备映射，不要求之前必须执行 prepare。

CLI 的 `--mappings FILE` 指定参与准备的个人映射表；没有指定时使用安装目录的 `personal/mappings.json`。
低层 API `convertDesign(snapshot, mappingTable, options)` 则接收调用方给定的映射表，不自动替调用方读取个人配置。

### 3.3 投影与过滤不是一件事

`projectMappings` 改变“本次要画哪些对象”：显式省略器件/引脚、按选项省略禁用实例、移除孤立外部端口，并更新相应网络成员、symbol 与正式接口。
原始快照保持不变，变更记录在报告中。

之后 adapter 再筛选参数：仅保留映射表指定的 properties 和 effectiveCdfParameters。这个结果才是返回的 `filtered.snapshot.json`。
它不只是“把高阶参数删掉的原文件”，还包含前面的投影结果。

孤立 pin 的原接口信息保存在报告里。目标不再声明这些正式接口；引起的已知外部边界单端警告独立记录，不等于关闭整个 ERC。

### 3.4 生成目标工程

`generic-box.ts` 为需要兜底的实例生成外部模块定义，依据源引脚短线/方框推断边，固定引脚节距，并保留原实例的旋转镜像。
定义嵌入目标 `.icproj.json` 的 `externalSubcircuitDefinitions`，不是必须另带一份临时 symbol 文件。
定义虽然嵌在工程文件中，跨版本兼容性仍取决于目标 Canvas 的工程 schema 与导入支持。

Python 引擎将源坐标缩放/翻转到画布，放置器件，映射引脚和网络，参考原线段的走向与分支建立线路，再补目标引脚位置差异。
这是沿用源线图形并修正接头，不是只看 netlist 后全新自动布图。
实例名和参数表达式保留；W/L 等参数被复制不代表已完成工艺仿真模型绑定。

### 3.5 修正和校验

`refine_canvas.mjs` 的主要顺序是：

```text
box_routes：方框相关出线与局部电源分支
→ 原生方法生成衬底折线路径
→ bulk_routes：衬底支线接入点截短
→ 原生直接接触/同网拓扑规范化
→ 原生实例名称位置
→ 外部 pin 名称位置
→ 其余标签避让
→ 写出 refinement 记录
```

`validate_canvas.mjs` 随后检查格式、所有线路端点、网络命名合并、ERC、视觉诊断，并验证序列化回读和渲染 SVG。
允许某些视觉观察不等于格式或连接验证被关闭。
最后 TS 的 `validateConversion` 再比较投影后的源实例、网络成员与正式端口，避免只看“画面像”就算成功。

## 4. 用户能看见哪些文件

### SKILL 导出：1 个

| 文件 | 作用 | 保留建议 |
|---|---|---|
| 用户指定的 snapshot.json | 原始提取结果，是离线重复转换的输入 | 调试/复现时重要，不能被精简版本替代 |

### prepare：5 个

| 文件 | 作用 | 必须交给 convert 吗 |
|---|---|---|
| mappings.json | 用户可编辑的映射设置 | 使用这份设置时需要 |
| devices.json | 结构化扫描/准备结果、实例和状态 | 否，未来前端可直接用返回对象 |
| preview.txt | 给人读的器件概览 | 否，与 devices 有重叠 |
| catalog.json | 所有符号及当前转换支持情况 | 否，是参考资料 |
| catalog.md | catalog 的可读版本 | 否，不必每个设计重复生成 |

### convert 成功：默认 2 个，调试 10 个

默认只保存 `project.icproj.json` 与精简 `report.json`；`--preview` 额外保存 `preview.svg`。
`--debug` 保存下表全部文件，并加上实际使用的 `mappings.json`、`config.json` 和 `presentation.json`，共 10 个。
精简报告保留配置、警告、简化记录和校验结果，但不包含逐实例 placement、参数来源、完整映射及逐次路由处理记录。完整内容仍可在调试报告中查看。

| 文件 | 作用 | 保留建议 |
|---|---|---|
| project.icproj.json | 最终可编辑工程，包含通用方框定义 | 必须 |
| source.snapshot.json | 输入原始快照的再保存副本 | 调试保留；用户已有原文件时有重复 |
| filtered.snapshot.json | 投影、参数过滤后的输入 | 定位映射/过滤问题时保留 |
| report.json | 配置、参数来源、源/目标对应、简化情况、校验摘要 | 建议保留，解释本次到底做了什么 |
| validation.json | 原生详细校验结果 | 调试保留；与 report 内 validation 重复 |
| refinement.json | 路由/标签修改前后与阶段耗时 | 算法调试需要，普通使用不必一直存 |
| preview.svg | 快速查看转换结果 | 可选；不是可编辑工程的替代品 |
| mappings.json | 本次使用的有效器件映射 | 复现映射决策时保留 |
| config.json | 补齐默认值并应用 CLI 覆盖后的个人配置 | 复现用户策略时保留 |
| presentation.json | 传给 Python 转换器的展开后显示配置 | 跨语言调试时保留 |

正常 CLI 不自动生成 PNG。`editor-desktop.png`、计时 JSON、files.json、测试报告等来自测试脚本，不是产品运行必需文件。
API 本身仍返回完整对象，由调用方决定是否保存；输出分层只改变 CLI 的发布行为。

## 5. 程序内部的临时文件

当前跨语言调用通过文件传递，而不是 stdin JSON 协议。

| 所在阶段 | 临时文件 | 目的 |
|---|---|---|
| TS 创建 `/tmp/virtuoso-canvas-*` | snapshot.json | 精简输入交给 Python |
| 同上 | mapping.json | 每实例规则、目标 symbol 定义、scale/grid |
| 同上 | presentation.json | 本次显示配置 |
| Python 创建 `/tmp/canvas-convert-*` | result.icproj.json | 未验收工程，供 refine/validate 原地处理 |
| 同上 | result.refinement.json | 布局处理记录 |
| 同上 | result.validation.json | 校验记录 |
| 同上 | result.svg | 校验时生成的原生预览 |
| 同上 | result.icproj.report.json | Python 汇总报告；CLI 最后改名为 report.json |
| 同上 | source-unconnected-box-pins.json | 已知源端未连接的方框引脚清单 |
| 同上 | source-omitted-port-interfaces.json | 已移除孤立端口的外部边界信息 |

Python 校验通过后将产物复制到 adapter 的临时目录，TS 读取后返回结果，最后清理临时目录。
这里存在“两层临时目录”和“反复读写 JSON”，对当前 Python/Node 隔离实现有用，但并不是业务上必须长期保留两套文件。
不应现在直接删掉某个临时文件：其中一部分是另一进程的真实输入。

## 6. 结果状态和失败行为

- `success`：转换、格式和连接检查通过，没有需要用户查看的诊断。
- `success_with_warnings`：工程可交付，但报告中存在源设计警告、布局观察、ERC warning 或用户明确选择的简化。单纯的能力说明记录在 `information`，不改变状态。
- `error`：不能交付可信工程，不生成工程或预览。
- `cancelled`：用户主动取消，不生成成功目录或失败诊断目录。

- CLI 发布成功目录使用暂存目录加 rename，已有目标目录拒绝覆盖。
- convert 在参数解析完成后发生失败，会写入 `OUT.failed/error.json`，记录 input/mapping/conversion/publish 阶段；重复失败使用 `.failed-1` 等编号，绝不覆盖旧诊断。
- 有子进程输出时保存 `process.log`；Python 已生成的 validation/refinement 会从临时目录取回。失败目录里不放正式工程，也不放 SVG 预览。
- `--debug` 失败时额外保存已经读取的原始快照、实际映射及显示配置。未到达的阶段不会假造文件。
- stderr 的 JSON 用 `diagnosticsDirectory` 指向持久目录。日志里的旧 `/tmp` 路径仍是过程记录，不能继续使用它作为输出路径。
- 无写权限等原因可能连诊断目录也无法创建，此时终端保留原始错误并附加 `diagnosticsWriteError`，不会把保存诊断失败冒充原始转换原因。
- 异常发生得更早时可能没有 `validation.json`。SKILL 写盘中途失败也还没有完善的原子发布保证。

诊断是否阻断以严重度和可交付性为准。Analog Canvas 的 ERC/视觉 `error` 阻断；`warning`、`info` 进入报告但允许导出。源与目标网络成员不一致、工程 schema 无效、master 缺失、映射无效属于错误；悬空引脚、标签重叠、线路穿框、总线简化等属于警告。具体错误码保留在 `error.code`，稳定的大类位于 `error.category`。

## 7. 旧流程不要与当前流程混用

```text
scan → inventory.json
recommend → proposal.json + decisions.json + preview.txt
confirm → mapping-package.json + confirmation.json
convert --package → 使用旧确认包
```

它仍留在代码里做兼容，不是今天推荐用户走的必经流程。
`rules/builtin/common.json`、Proposal/Decisions/MappingPackage schema，以及相关函数主要服务这条旧路径。
当前流程是 `prepare / save-mappings / convert --mappings`，这里的 mappings.json 与旧 mapping-package.json 不是同一格式。
某些新行为只走当前映射表投影路径，旧入口不能自动认为具备完全相同的选项支持。

## 8. 中间文件是否必要：建议讨论的结论

建议未来把“程序内部必须使用”和“用户目录必须保存”分开：

| 使用方式 | 建议对外保留 |
|---|---|
| 普通导出 | project.icproj.json + 简洁 report.json；预览可选 |
| 调试导出 | 原始/精简快照、实际配置和映射、完整 refinement/validation、预览 |
| 失败 | 固定诊断目录，error.json + 日志；有可用预览时保留 |
| 查看可用器件 | 安装级 catalog，不必每次 prepare 复制一套 |

普通/调试输出与固定失败诊断已落实。catalog 去重仍是建议；尚未删除旧流程、重命名 legacy 或合并模块。
当前最明显的冗余是源快照副本、重复校验 JSON、每次重复 catalog；而原始快照和精简快照内容不同，不应误认为可以无条件互相替代。

## 9. 建议阅读顺序

1. 本文的主流程与文件表。
2. CLI `main.ts`：用户命令最终调用什么、保存什么。
3. adapter `src/index.ts` 的 `convertDesign`：整个转换怎么组织。
4. `mapping-table.ts` 的 `projectMappings`：哪些数据会被省略或改变。
5. Python `convert`：如何形成工程、网络和基础线。
6. `refine_canvas.mjs` 及各布局模块。
7. `validate_canvas.mjs` 与 TS `validateConversion`：如何判断成功。
8. 最后看 SKILL 和旧流程细节，不必一开始同时理解所有语言和兼容逻辑。

下一步应结合新输出方式确认使用体验，再统一具体场景错误码和检查；不建议先为了文件树好看而移动代码。
